## О проекте

**Бизнес-контекст.** Компания CalmFruits развивает онлайн-каталог товаров. Пользователи ищут товары через поисковую строку, но классический поиск по ключевым словам не всегда хорошо справляется с реальными пользовательскими запросами.

**Гипотеза.** Команда хочет проверить, можно ли улучшить поиск с помощью векторных представлений запросов и товаров. Для этого нужно построить MVP системы семантического поиска.

**Ваша роль.** Вы выступаете в роли DS-специалиста, который получает каталог товаров и историческую разметку релевантности товаров. Ваша задача — построить базовую систему поиска, сравнить несколько подходов и объяснить бизнесу:

- стоит ли использовать векторный поиск;
- в каких случаях он помогает, а когда ошибается;
- какие улучшения стоит рассмотреть дальше.

**Данные.**

В проекте четыре файла (Parquet, S3-бакет `s3-ds-source`, endpoint `https://storage.yandexcloud.net`). Три из них — рабочие, один — служебный.

| Файл | Что внутри | Где нужен |
|---|---|---|
| `wb_products_raw_sample.parquet` | сырой каталог: 200 000 строк, 65 корневых категорий; колонки `imt_id`, `nm_id`, `imt_name`, `subj_name`, `subj_root_name`, `nm_colors_names`, `vendor_code`, `description`, `brand_name` | нед. 1 (EDA), нед. 2 (подготовка каталога) |
| `wb_products_dedup.parquet` | 4256 оценённых карточек (2580 из них привязаны к запросам train/test); задаёт множество `imt_id` для каталога оценки | нед. 2 |
| `queries_synthetic_train.parquet` | пары «запрос — товар» с `relevance` 0–3; `query_id`, `query_text`, `item_id` (= `imt_id`) | нед. 1–3 |
| `queries_synthetic_test.parquet` | та же структура, запросы не пересекаются с train | **один** финальный прогон (нед. 3) |

**Итоговые артефакты проекта:**

- Jupyter-тетрадь с EDA, пайплайном и оценкой качества системы;
- эксперименты, логируемые в MLflow;
- этот документ, заполненный по ходу работы;
- дополнительная часть проекта — Streamlit-приложение (бонус, на зачёт не влияет).

**Ключевые наблюдения по ТЗ (мои заметки):**

- Объект индексации — карточка (`imt_id`), а не артикул (`nm_id`): иначе один товар будет конкурировать сам с собой. Разметка ссылается именно на `imt_id`.
- Каталог оценки ограничен 4256 карточками из `wb_products_dedup.parquet`; из них только 2580 имеют разметку. Остальные ~1676 карточек в разметке не встречаются — это важно для трактовки «неразмеченных» товаров в выдаче.
- Тексты для эмбеддинга (`product_text`) нужно собрать самому из названия, категории, описания, бренда, цвета; товары без описания остаются с названием и категорией.
- Запросы синтетические, короткие, в свободной форме. Возможны смещения: разметка сгенерирована (вероятно, LLM), запросы могли быть написаны «глядя» на карточку.
- Test используется один раз, в самом конце. Подбор гиперпараметров и сравнение подходов — только на train (по запросам, без утечки: группировка по `query_id`).
- Ревьюеры требуют: EDA (пропуски, дубликаты, длины текстов, категории, ≥2 визуализации), разбивка без утечки по запросам, эмбеддинги для всех товаров каталога, фиксированный K из ТЗ, ≥2 из 3 метрик посчитаны верно, ≥3 осмысленных коммита, данные не в репозитории.

### Вопросы про используемые для оценки метрики.

**3.1**
- Что известно: релевантность градуированная, 0–3; задача — ранжирование, метрики нужно выбрать самим; ревьюер проверяет K «по ТЗ».
- Вопрос/уточнение: Какие метрики главные (NDCG@K, Recall@K, Precision@K, MRR, MAP) и какие значения K фиксируем (например, 5 и 10)? По какой из них принимается решение?
- Ответ: Считаем и показываем весь набор K ∈ {1, 3, 5, 10} — малые K отражают качество верха выдачи, K=10 — общее качество ранжирования; свои дополнительные K добавлять можно, убирать из этого набора нельзя. Решение принимается в первую очередь по NDCG@10 и NDCG@5.

**3.2**
- Что известно: для Precision/Recall нужна бинарная релевантность, а разметка градуированная 0–3.
- Вопрос/уточнение: С какого значения `relevance` считать товар релевантным для бинарных метрик (≥1, ≥2 или только 3)? Какие «гейны» использовать в NDCG (линейные `rel` или `2^rel − 1`)?
- Ответ: Порог бинаризации — фиксированный `relevance ≥ 2` (релевантные + максимально релевантные считаются релевантными, «частично релевантные» = 1 уходят в ноль); порог фиксирован для сопоставимости результатов у всех студентов, итоговые числа в отчёте — именно по этому порогу. NDCG считается по полной шкале 0–3 без бинаризации, `gain = 2^rel − 1`; разделение намеренное — NDCG умеет учитывать градации, бинарным метрикам нужна чёткая граница.

**3.3**
- Что известно: размечены не все товары для каждого запроса; в каталоге оценки 4256 карточек, 2580 привязаны к запросам.
- Вопрос/уточнение: Как трактовать товары без разметки для запроса — как нерелевантные (0) или исключать из ранжирования? Из чего формируется выдача при оценке: из всего каталога оценки (4256) или только из размеченных под этот запрос товаров? Что делать с запросами, у которых нет ни одного релевантного товара?
- Ответ: Товар, отсутствующий в разметке запроса, считается нерелевантным (0) — это финальная трактовка, стандартное соглашение для пулированной разметки, менять не нужно. Единственное условие — честно зафиксировать это как ограничение оценки в финальных выводах (часть хороших товаров могла быть просто не размечена).

**4.3**
- Что известно: в ТЗ предусмотрено дообучение модели на train-разметке; test — один финальный прогон.
- Вопрос/уточнение: Можно ли дообучать эмбеддинги на train-разметке и как принимаем модель — по внутренней валидации (разбиение train по запросам) с последующим единственным прогоном на test? Какой формат финальной презентации и в каком виде оформлять «язык бизнеса»?
- Ответ: Дообучение желательно, но не обязательно для зачёта. Обязательно — минимум два осмысленных эксперимента (одна гипотеза = одно изменение), валидация без утечки и логирование всех прогонов в MLflow. Дообучение — самый сильный из возможных экспериментов и рекомендуется, но его может заменить любая другая пара качественных экспериментов (например, гибрид + смена модели/шаблона текста), доведённых до метрик и выводов. «Один финальный прогон на test» — про дисциплину, а не про число моделей: к test обращаются один раз, когда конфигурация уже выбрана на train/валидации, без итеративной подстройки по test; при этом в этот финальный прогон можно и нужно включить все кандидаты сразу (лексический baseline, семантический baseline, финальную модель) для единой сравнительной таблицы.

На «черное платье на выпускной» семантика выигрывает — понимает стиль/повод и находит «Двухстороннее платье с эффектом бандажа», «Корсетное платье», «Элегантное летнее платье» без буквального совпадения слов. **Предварительный вывод для бизнеса (черновой, до экспериментов недели 3):** в текущей конфигурации внедрять именно эту семантическую модель как замену лексическому поиску не стоит — она работает хуже baseline. Прежде чем делать выводы о пользе векторного поиска в принципе, нужно попробовать более подходящую модель эмбеддингов и/или дообучение (неделя 3), а также гибридный подход, который бы использовал сильные стороны обоих методов.

## 3. Эксперименты по улучшению

Для каждого эксперимента фиксируйте:

- гипотезу;
- изменения относительно базового пайплайна;
- результат по метрикам,
- вывод — считаем результат удовлетворительным или нет.

Каждый эксперимент должен быть залогирован в MLflow.

**Идеи для экспериментов (выберите и дополните своими; провести 2–3, а не все):**

- другой шаблон `product_text`;
- другая модель эмбеддингов;
- дообучение эмбеддера на парах «запрос — релевантный товар» из train (проекция поверх замороженного энкодера / разморозка N верхних слоёв / полный fine-tuning / LoRA);
- гибридный поиск — комбинация лексического и семантического (взвешенная сумма, RRF, реранкинг);
- предобработка текста — лемматизация, удаление стоп-слов для TF-IDF;
- изменение параметров векторизации (`ngram_range`, `max_features`).

**Правило:** один эксперимент — одна гипотеза — одно изменение относительно baseline. Гипотеза должна опираться на конкретное наблюдение из EDA/анализа ошибок недели 2, а не только на «хочу попробовать».
**Данные:** train можно дальше делить на обучение/валидацию — это независимые процессы, отдельные от финального прогона на test (только один раз, после выбора лучшей конфигурации).
**GPU:** лимит 10 часов, подключать только в конце, когда остальные эксперименты (без дообучения) уже проведены.

**Эксперимент 1**
- Гипотеза: Модель `paraphrase-multilingual-MiniLM-L12-v2` обучена на задаче paraphrase similarity (сходство перефразировок), а не на задаче query-to-item retrieval — это разные цели: близость "запрос ~ товар" концептуально отличается от близости "текст A ~ текст B, означающих одно и то же". Модели семейства E5 (`intfloat/multilingual-e5-base`) специально обучены контрастивным способом именно на парах "запрос-документ" с явными префиксами `query:`/`passage:`, поэтому должны точнее разделять релевантные и нерелевантные товары для конкретного запроса. Ожидаем прирост NDCG@10 относительно семантического baseline (0.1495), возможно — приближение к лексическому baseline (0.4461) или превышение его.
- Что меняем: Только модель эмбеддингов (было `paraphrase-multilingual-MiniLM-L12-v2`, стало `intfloat/multilingual-e5-base`) и добавление обязательных для E5 префиксов `"query: "` / `"passage: "`. Всё остальное — тот же `product_text`, тот же каталог оценки, тот же способ подсчёта метрик.
- Результат (метрики):

| method | k | Precision@k | Recall@k | HitRate@k | NDCG@k | MRR@10 |
|---|---|---|---|---|---|---|
| semantic (MiniLM, baseline) | 10 | 0.0489 | 0.1453 | 0.2729 | 0.1495 | 0.1330 |
| **semantic_e5_base** | 10 | **0.1579** | **0.6345** | **0.7700** | **0.4929** | **0.5507** |
| lexical (TF-IDF, для сравнения) | 10 | 0.0821 | 0.3229 | 0.4557 | 0.4461 | 0.1880 |

- Вывод: **Гипотеза принята**, хотя эффект оказался заметно скромнее, чем в первой версии этого эксперимента (после добавления цвета в `product_text` разрыв сократился). Замена только модели эмбеддингов (MiniLM → e5-base) дала: NDCG@10 0.149 → **0.493** (+0.344, рост более чем в 3 раза), MRR@10 0.133 → **0.551** (более чем в 4 раза), Recall@10 0.145 → **0.634**. **e5-base по-прежнему превосходит не только предыдущую семантическую модель, но и лексический baseline по всем пяти метрикам на всех K** (NDCG@10: 0.493 против 0.446), хотя преимущество над лексикой теперь не такое явное, как было до изменения `product_text` (там разрыв был почти трёхкратным; сейчас ≈10.5% относительно). Качественно: на «черное платье на выпускной» e5 нашёл товар с названием почти дословно совпадающим с запросом («Платье женское нарядное вечернее на выпускной») — топ-1 с большим отрывом. На «бриджи зуавы» e5 теперь находит **все пять** позиций топ-5 из категории «Бриджи» — против полного провала у старой модели. Это подтверждает исходную гипотезу: retrieval-ориентированное обучение (запрос↔документ, а не парафраз↔парафраз) — принципиально важное свойство модели для данной задачи, а не второстепенная деталь. Проблема недели 2 была не в самой идее семантического поиска, а в неудачном выборе конкретной модели: векторный поиск может быть эффективнее лексического на этом каталоге — но только с правильно подобранной моделью эмбеддингов, и разрыв в пользу семантики чувствительнее к составу `product_text`, чем ожидалось изначально.

**Эксперимент 2**
- Гипотеза: Несмотря на то, что e5-base обходит лексический поиск по всем агрегированным метрикам, у подходов остаются разные сильные стороны: лексика надёжнее на точных словах/номенклатуре (например, «Худи Raava» — точное совпадение по «худи»), а e5 — на смысловых/перефразированных запросах. Если ошибки двух методов не полностью совпадают, объединение их ранжирований (Reciprocal Rank Fusion, RRF) должно дать прирост относительно каждого метода по отдельности — RRF — стандартный способ комбинировать разнородные системы ранжирования без необходимости калибровать шкалы скоров.
- Что меняем: Добавляется новый способ поиска — `search_hybrid_rrf`, объединяющий ранжирования `search_lexical` и `search_semantic_e5` через RRF. Сами модели и `product_text` не меняются (тот же TF-IDF-индекс, та же модель e5-base из эксперимента 1).
- Результат (метрики):

| method | k | Precision@k | Recall@k | HitRate@k | NDCG@k | MRR@10 |
|---|---|---|---|---|---|---|
| semantic_e5_base | 1 | 0.4486 | 0.2506 | 0.4486 | 0.3812 | 0.5507 |
| **hybrid_rrf** | 1 | 0.2814 | 0.1279 | 0.2814 | 0.2835 | 0.4062 |
| semantic_e5_base | 10 | 0.1579 | 0.6345 | 0.7700 | 0.4929 | 0.5507 |
| **hybrid_rrf** | 10 | 0.1416 | 0.5659 | 0.6971 | **0.5120** | 0.4062 |

- Вывод: **Гипотеза подтверждена частично, с оговоркой.** Гибрид RRF обгоняет чистый e5-base по NDCG@10 (0.5120 против 0.4929, +3.9% относительно) — по качеству ранжирования всей выдачи выигрывает. Но по остальным метрикам, особенно на верхних позициях, гибрид заметно хуже: Precision@1 падает с 0.4486 до 0.2814, MRR@10 — с 0.5507 до 0.4062. Иными словами, RRF улучшает глубокую выдачу, но ухудшает точность топ-1. Почему так вышло: e5-base сам по себе значительно сильнее лексического поиска, особенно на верхних позициях (Precision@1 0.449 против 0.099 у лексики). Равновесное объединение рангов через RRF не учитывает, что один источник системно точнее другого — он трактует оба метода как равноценных экспертов, из-за чего на k=1 это «портит» уверенные топы e5, подмешивая слабые результаты лексики; а на более глубокой выдаче (k=10) лексика иногда «вытаскивает» релевантные товары, которые e5 пропустил — за счёт этого NDCG@10 у гибрида чуть растёт. RRF — не универсальное улучшение и не чистый проигрыш: вклад в ранжирование на глубокой выдаче есть, но он не бесплатен — за это платится точность топ-1. Для будущих гибридных экспериментов логичнее взвешивание с явным перекосом в сторону e5, а не равновесный RRF.

**Эксперимент 3**
- Гипотеза: В эксперименте 2 равновесный RRF ухудшил результат, потому что трактовал лексику и e5 как равноценные источники, хотя e5 систематически точнее. Если дать e5 доминирующий вес, а лексике — маленький вклад (только как «подсказку» на случай точных терминологических совпадений), это должно сохранить высокую точность e5 в топе и, возможно, слегка приподнять метрики за счёт редких случаев, где лексика находит правильный товар по точному слову, а e5 — нет (как в примере «худи mego as»). Ожидаем результат на уровне чистого e5 или немного выше, а не провал, как в эксперименте 2.
- Что меняем: Способ комбинирования — вместо RRF по рангам, взвешенная сумма нормализованных скоров (`search_hybrid_weighted`, `w_semantic=0.85`, `w_lexical=0.15`). Модели и кандидаты те же, что и в эксперименте 2.
- Результат (метрики):

| method | k | Precision@k | Recall@k | HitRate@k | NDCG@k | MRR@10 |
|---|---|---|---|---|---|---|
| semantic_e5_base | 1 | 0.4486 | 0.2506 | 0.4486 | 0.3812 | 0.5507 |
| **hybrid_weighted** | 1 | 0.4371 | 0.2388 | 0.4371 | 0.3771 | 0.5452 |
| semantic_e5_base | 10 | 0.1579 | 0.6345 | 0.7700 | 0.4929 | 0.5507 |
| **hybrid_weighted** | 10 | 0.1587 | 0.6340 | 0.7671 | **0.5099** | 0.5452 |

- Вывод: **Гипотеза частично подтверждена, но эффект неоднозначный и на грани шума.** В отличие от RRF, взвешенный гибрид не проваливается на верхних позициях — просадка минимальна: Precision@1 0.437 против 0.449 у e5 (−2.6% относительно), MRR@10 0.545 против 0.551 (−1.0%). При этом по NDCG@10 гибрид обгоняет чистый e5: 0.5099 против 0.4929 (+3.4% относительно), почти вплотную подходя к результату RRF (0.5120), но без его резкой потери точности в топе. Небольшая примесь лексического сигнала (15%) иногда подтягивает правильный товар выше в середине выдачи, что даёт прирост NDCG, но ценой лёгкого «размытия» уверенных топ-1 позиций e5 — масштаб эффекта (±1–3%) достаточно мал, чтобы без теста на статистическую значимость не делать категоричных выводов на 700 запросах. Из трёх протестированных вариантов комбинирования взвешенный гибрид — лучший компромисс (почти не теряет точность топ-1 и даёт сопоставимый выигрыш в NDCG@10), но относительно простого решения (чистый e5-base) выигрыш мал и неоднозначен, а сложность — поддержка двух моделей и логики взвешивания — выше. **Финальный выбор лучшей конфигурации по итогам трёх экспериментов: `search_semantic_e5` (эксперимент 1)** — как более простое решение с сопоставимым качеством.


## 4. Трекинг экспериментов в MLflow

Опишите проделанные действия: Залогировали 6 прогонов в один эксперимент MLflow (`semantic_search_calmfruits`): `lexical_tfidf`, `semantic_minilm_baseline`, `semantic_e5_base`, `hybrid_rrf`, `hybrid_weighted` (все — на `eval_split="train"`) и `semantic_e5_base_FINAL_TEST` (на `eval_split="test"`, единственный прогон по тестовым данным). В каждом run залогированы обязательные параметры (`method`, `eval_split`, `catalog_size`, `relevance_threshold`) и дополнительные параметры конфигурации (модель эмбеддингов, способ комбинирования для гибридов, вес `W_SEMANTIC`/`RRF_K`, шаблон `product_text`, параметры TF-IDF). Обязательные метрики (`ndcg_at_10`, `recall_at_10`, `precision_at_5`, `mrr`) залогированы в каждом run, плюс полный набор Precision/Recall/HitRate/NDCG по всем K для полноты. В качестве артефактов сохранены: сводная CSV-таблица метрик по каждому run и копия golden-сета (train и test — отдельные JSON-файлы). При настройке подключения понадобилось отдельно прописать S3-креды под MLflow (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`MLFLOW_S3_ENDPOINT_URL`) для загрузки артефактов в объектное хранилище, а также решить конфликт версий `boto3`/`botocore`/`aiobotocore` в окружении. Логирование проверено официальным скриптом `check_mlflow.py semantic_search_calmfruits --env-file .env` — результат: «ВСЁ В ПОРЯДКЕ: эксперимент, прогоны, метрики и параметры на месте». Дополнительно `log_run` сделан устойчивым к недоступности сервиса MLflow (курсовой сервер периодически отдавал `503`): локальные CSV-артефакты (`summary_*.csv`, `per_query_*.csv`) теперь сохраняются всегда, независимо от того, доступен MLflow или нет, а подключение к `mlflow.set_experiment` оборачивается в `try/except` с флагом `MLFLOW_AVAILABLE` — если сервис недоступен, сами прогоны в MLflow просто пропускаются с явным сообщением в выводе, без падения тетради.

**Обязательный минимум (проверяется `check_mlflow.py`):**
- один эксперимент на проект, отдельный run на каждую конфигурацию, осмысленные имена run (`semantic_bge_m3`, не `run_7`)
- минимум 2 успешных прогона
- метрики в каждом run: `ndcg_at_10`, `recall_at_10`, `precision_at_5`, `mrr`
- параметры в каждом run: `method`, `eval_split`, `catalog_size`, `relevance_threshold`
- параметры конфигурации: подход, модель эмбеддингов, шаблон `product_text`, порог бинаризации, размер каталога, параметры векторизации
- артефакты: таблица метрик по каждому запросу, сводная таблица, графики сравнения, копия golden-сета
- команда проверки: `python check_mlflow.py <название эксперимента> --env-file ../.env`

Эксперимент 1 показал кратный скачок относительно обоих baseline (NDCG@10 0.4929 против 0.4461 у лексики и 0.1495 у MiniLM-семантики, MRR@10 0.5507 против 0.1880 и 0.1330) — модель, специально обученная для retrieval, принципиально сильнее и лексики, и общей paraphrase-модели. Относительно e5-base гибриды (RRF и взвешенный) дают небольшой прирост NDCG@10 (0.5120 и 0.5099 против 0.4929), но ценой просадки точности в топе — особенно у RRF (MRR@10 падает до 0.4062). Без отдельного теста на значимость этот выигрыш не оправдывает усложнение пайплайна, поэтому выбор — чистый e5-base. Финальный тест (300 ранее не видимых запросов) подтвердил устойчивость: NDCG@10=0.4908 на test почти совпадает с train (0.4929), а разрыв с лексикой на том же сплите сохраняется (0.4908 против 0.4276).

**Ограничения оценки:**

- **Разметка синтетическая и, вероятно, сгенерированная моделью**, а не собранная от реальных пользователей — характер запросов (короткие, иногда с обрывками брендов на латинице) может не полностью отражать реальные пользовательские формулировки.
- **Каталог оценки (4 256 карточек) намного меньше реального каталога** («Одежда»+«Обувь» после подготовки — 48 376 карточек, а в исходной выгрузке 65 категорий и 200 000 строк). Результаты нельзя напрямую экстраполировать на работу системы по всему ассортименту без переоценки.
- **Разметка неполная** — из 4 256 карточек пула асессоров только 2 580 фактически связаны хотя бы с одним запросом; методика «не в разметке → нерелевантно» занижает метрики для действительно хороших, но не оценённых товаров (наглядно видно в разделе «Каталог для поиска и оценки»: NDCG@10 на полном подготовленном каталоге почти в 11 раз ниже, чем на каталоге оценки — 0.0436 против 0.4607).
- **Модель эмбеддингов не дообучена на домене** — использована готовая предобученная `multilingual-e5-base`, без файнтюна на данных CalmFruits; часть найденного прироста может увеличиться ещё сильнее при дообучении (не пробовали из-за лимита GPU и объёма недели).
- **Оценка ограничена категориями «Одежда» и «Обувь»** — выводы не переносятся автоматически на остальные 63 категории каталога, где могут быть свои особенности текста и терминологии.
- **Один прогон на test** — по протоколу теста нет возможности перепроверить устойчивость на другом test-сплите; статистическая значимость различий между методами не проверялась (например, бутстрэпом), различия в единицы процентов между гибридами и e5-base могут быть шумом.

**5.2. Качественный анализ ошибок** 

Числа из сводной таблицы (5.1) показывают, что лучшая конфигурация работает заметно лучше остальных в среднем, но не объясняют, на каких именно запросах она всё ещё ошибается. Среди 10 худших по NDCG@10 запросов **все 10 имеют NDCG = 0.0** (всего таких запросов 33 из 700, 4.7%). У каждого есть от 14 до 30 размеченных товаров в golden-сете, но релевантных среди них (`relevance ≥ 2`) почти всегда ровно один (у «блузки len» — 2). То есть проблема не в бедности каталога на нужную категорию, а в том, что системе нужно найти единственный конкретный товар среди множества похожих — рассмотрим два показательных случая.

**Случай 1: «хлопковые рубашки».** Единственный размеченный релевантный товар — `imt_id=10049000`. В топ-10 e5 — сплошь обобщённые «Рубашка» / «Рубашка мужская» / «Рубашка с длинным рукавом из хлопка» без конкретики, нужный товар не попал в выдачу вообще. Категория распознана верно, но уточняющий атрибут «хлопковые» модель не использует как фильтр — он просто теряется на фоне общего смысла запроса.

**Случай 2: «футболки puma».** Единственный размеченный релевантный товар — `imt_id=10172300`. Первые 5 позиций топ-10 e5 — футболки именно бренда Puma («Футболка PUMA EXO-ADAPT SS Tee», «Футболка MAPM Graphic Tee» и т.д.), то есть бренд и категория распознаны верно, но конкретно размеченный товар среди нескольких похожих вариантов того же бренда не попал в выдачу. При этом ближе к концу топ-10 выдача начинает терять и категорию — на позициях 6–10 появляются «Юбка», «Леггинсы», «Топ», никак не связанные с запросом. Это говорит не только о недостаточной точности среди похожих товаров бренда, но и о том, что после первых уверенных совпадений модель быстро теряет уверенность и скатывается в общую «похожесть по стилю/духу», а не по типу товара.

**Паттерн по всем 10 худшим.** Минимум 5 из 10 запросов («футболки puma», «рубашки zolla», «костюмы didriksons», «платья bullkin wear», «рубашки mexx») содержат название бренда/поставщика на латинице — паттерн согласуется с кейсом 2. Остальные («хлопковые рубашки», «кожаные ботинки на молнии», «футболки с нашивкой», «босоножки olivia», «блузки len») — запросы «категория + уточняющий атрибут» (материал, застёжка, принт), где модель уверенно даёт общую категорию, но не учитывает уточнение — паттерн из кейса 1.

**Общий вывод по ошибкам.** Оставшаяся слабость e5-base — два воспроизводимых паттерна: (1) потеря уточняющего атрибута (материал, деталь кроя, декор) на фоне общей категории; (2) недостаточная точность при выборе среди нескольких похожих товаров одного бренда, усугубляемая тем, что после первых релевантных позиций выдача может быстро «расползтись» по не связанным с запросом категориям. Оба — кандидаты для дальнейшей работы: первый может решаться точечной лексической фильтрацией по ключевым словам-атрибутам поверх векторного поиска, второй — дообучением/реранкингом на доменных парах «запрос-карточка» (см. 5.4).

**5.3. Рекомендация бизнесу** 

**Да, векторный поиск стоит внедрять** — но не в виде первой опробованной конфигурации, а с моделью эмбеддингов, специально обученной под задачу поиска (retrieval), а не под общее сходство текстов. Разница принципиальна: первая протестированная модель (`paraphrase-multilingual-MiniLM`) проиграла даже простому лексическому поиску (NDCG@10 0.15 против 0.45), тогда как retrieval-модель (`multilingual-e5-base`) обошла лексику на ≈10.5% относительно (NDCG@10 0.49 против 0.45) без какого-либо дообучения — и этот разрыв подтвердился на отложенном test (0.49 против 0.43, ≈14.8%).

**Форма внедрения:** полная замена лексического поиска семантическим (`e5-base`) для категорий «Одежда»/«Обувь» — эксперименты не показали убедительной пользы от гибридизации с лексикой (прирост по NDCG@10 в пределах 2–4 п.п. при заметной просадке точности в топе), а значит, не стоит усложнять систему поддержкой двух движков ради ожидаемого прироста в пределах статистического шума.

**Где помогает:** запросы, сформулированные через стиль/повод/назначение, а не точное название («черное платье на выпускной» → «Платье женское нарядное вечернее на выпускной»), и запросы с редкой профессиональной терминологией, которую e5 смог связать с категорией лучше, чем прошлая модель («бриджи зуавы»).

**Где может ошибаться:** запросы с шумными вставками (обрывки брендов на латинице вперемешку с русским текстом) — на них не справлялась ни одна из протестированных моделей одинаково хорошо; см. качественный разбор в 5.2.

**Конкретная быстрая доработка перед запуском.** Качественный анализ (5.2) показал, что минимум 5 из 10 худших запросов — это паттерн «категория + бренд на латинице» (`рубашки zolla`, `футболки puma`, `костюмы didriksons`, `платья bullkin wear`, `рубашки mexx`): эмбеддинг не умеет точно учитывать бренд, зашитый в свободный текст запроса. Точный (не векторный) матч бренда с последующим фильтром/буст-скором для товаров этого бренда — дешёвая доработка, устраняющая заметную долю оставшихся ошибок без переобучения модели. Рекомендуем внедрить её в первую очередь, до вложений в дообучение эмбеддера (см. 5.4).

**5.4. Дальнейшие шаги** 

- Собрать реальные пользовательские логи запросов и кликов вместо синтетической разметки — позволит проверить, действительно ли перенос выводов с синтетических запросов на реальные корректен, и снимет ограничение «разметка сгенерирована, а не собрана от пользователей».
- Дообучить `e5-base` на доменных парах «запрос-релевантный товар» из train (например, через контрастивное дообучение верхних слоёв) — раз готовая модель уже дала прирост без дообучения, специализация под каталог CalmFruits может дать дополнительный выигрыш, особенно на слабом месте — шумных запросах.
- Перейти на приближённый поиск (ANN-индекс, например HNSW/FAISS) при масштабировании с 4–48 тыс. карточек на полный каталог (200 000+ строк, 65 категорий) — полный перебор (`brute-force`) станет неоправданно медленным на таком объёме, а ANN даёт почти ту же точность на порядки быстрее.
- Добавить фильтрацию по атрибутам (бренд, цвет, размер, категория) поверх векторного поиска как отдельный слой — это позволит точно обрабатывать запросы с явными атрибутами («красное платье», «Nike кроссовки»), не полагаясь только на то, что эмбеддинг «поймёт» атрибут из текста.
- Расширить оценку на остальные категории каталога — текущие выводы сделаны только для «Одежды»/«Обуви»; для внедрения на весь ассортимент потребуется отдельная разметка и повторная проверка на других товарных группах.

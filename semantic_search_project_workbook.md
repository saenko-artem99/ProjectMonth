## О проекте

**Бизнес-контекст.** Компания CalmFruits развивает онлайн-каталог товаров. Пользователи ищут товары через поисковую строку, но классический поиск по ключевым словам не всегда хорошо справляется с реальными пользовательскими запросами.

**Гипотеза.** Команда хочет проверить, можно ли улучшить поиск с помощью векторных представлений запросов и товаров. Для этого нужно построить MVP системы семантического поиска.

**Ваша роль.** Вы выступаете в роли DS-специалиста, который получает каталог товаров и историческую разметку релевантности товаров. Ваша задача — построить базовую систему поиска, сравнить несколько подходов и объяснить бизнесу:

- стоит ли использовать векторный поиск;
- в каких случаях он помогает, а когда ошибается;
- какие улучшения стоит рассмотреть дальше.

**Данные.**

В проекте четыре файла (Parquet, S3-бакет `s3-ds-source`, endpoint `https://storage.yandexcloud.net`). Три из них — рабочие, один — служебный.

| Файл | Что внутри | Где нужен |
|---|---|---|
| `wb_products_raw_sample.parquet` | сырой каталог: 200 000 строк, 65 корневых категорий; колонки `imt_id`, `nm_id`, `imt_name`, `subj_name`, `subj_root_name`, `nm_colors_names`, `vendor_code`, `description`, `brand_name` | нед. 1 (EDA), нед. 2 (подготовка каталога) |
| `wb_products_dedup.parquet` | 4256 оценённых карточек (2580 из них привязаны к запросам train/test); задаёт множество `imt_id` для каталога оценки | нед. 2 |
| `queries_synthetic_train.parquet` | пары «запрос — товар» с `relevance` 0–3; `query_id`, `query_text`, `item_id` (= `imt_id`) | нед. 1–3 |
| `queries_synthetic_test.parquet` | та же структура, запросы не пересекаются с train | **один** финальный прогон (нед. 3) |

**Итоговые артефакты проекта:**

- Jupyter-тетрадь с EDA, пайплайном и оценкой качества системы;
- эксперименты, логируемые в MLflow;
- этот документ, заполненный по ходу работы;
- дополнительная часть проекта — Streamlit-приложение (бонус, на зачёт не влияет).

**Ключевые наблюдения по ТЗ (мои заметки):**

- Объект индексации — карточка (`imt_id`), а не артикул (`nm_id`): иначе один товар будет конкурировать сам с собой. Разметка ссылается именно на `imt_id`.
- Каталог оценки ограничен 4256 карточками из `wb_products_dedup.parquet`; из них только 2580 имеют разметку. Остальные ~1676 карточек в разметке не встречаются — это важно для трактовки «неразмеченных» товаров в выдаче.
- Тексты для эмбеддинга (`product_text`) нужно собрать самому из названия, категории, описания, бренда, цвета; товары без описания остаются с названием и категорией.
- Запросы синтетические, короткие, в свободной форме. Возможны смещения: разметка сгенерирована (вероятно, LLM), запросы могли быть написаны «глядя» на карточку.
- Test используется один раз, в самом конце. Подбор гиперпараметров и сравнение подходов — только на train (по запросам, без утечки: группировка по `query_id`).
- Ревьюеры требуют: EDA (пропуски, дубликаты, длины текстов, категории, ≥2 визуализации), разбивка без утечки по запросам, эмбеддинги для всех товаров каталога, фиксированный K из ТЗ, ≥2 из 3 метрик посчитаны верно, ≥3 осмысленных коммита, данные не в репозитории.
